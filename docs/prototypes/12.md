# Prototype 12 — `euclid2-typegpu`: a WebGPU renderer for the 2D canvas

**Status:** charter only. P11 established that scene evaluation preserves object identity across ticks — which is exactly what a GPU renderer needs: stable identity ⇒ stable buffer slots, so per-tick uploads become patches instead of rebuilds. This prototype renders the euclid2 world layer (strokes, fills, grid) with TypeGPU/WebGPU while SVG keeps the HUD (point marks, handles, sliders) and the DOM stays in charge of layout and events. It runs as a **parallel scene kind** (`kind: "euclid2-typegpu"`) so the SVG renderer is never at risk.

## Why a renderer, and why now

The SVG renderer rasterizes with the browser: every fill is a tessellated path, every stroke a `<path>` re-updated on camera moves, and zooming past a few thousand nodes hits SVG serialization and re-layout costs that no eval-layer caching can touch. In 3D none of this exists as an option — GPU rendering is the only path. Proving the 2D canvas on the GPU is the smallest step that derisks the machinery we will need everywhere: device/root lifecycle under Solid, per-tick buffer writes from eval output, camera as a uniform, picking under a GPU renderer.

**The P11 connection:** trace nodes are identity-stable across draft ticks (memo hits replay the previous eval's value objects). That means the renderer can key GPU resources on node identity — a node keeps its buffer slot until it dies, and a drag tick writes one new vertex/instance slot instead of re-uploading the world. This is the property the whole prototype is built to exploit.

## Candidate architectures (to be narrowed by spike)

1. **SDF-driven fragments.** Every node carries an analytic distance function; a fullscreen-ish pass evaluates `sdLine`/`sdDisk`/polygon SDFs per pixel with 1px AA via `smoothstep(fwidth, 0, d)`. `csg2` boolean ops map *directly* onto SDF operators (`min` = union, `max(-d)` = difference, `max` = intersection) — the diff/roundOffset chains we already cache could render without tessellation at all. Costs: per-pixel work scales with scene size unless bounded (the skill's early-out pattern via AABBs; P11's pick AABBs are the same boxes), and polygon SDFs with many vertices are the hard case.
2. **Instanced triangles.** CPU tessellation (already exists in `evaluateRegions`/fill paint) feeds vertex/index buffers; strokes as instanced segment quads or thick-line capsules. Predictable per-frame cost, but reintroduces CPU geometry work the SDF route avoids, and AA requires MSAA (4x memory bandwidth).
3. **Hybrid.** SDF for circles/lines/CSG-of-SDFs, triangles for filled polygons whose vertex counts blow past a shader-friendly bound. Likely the honest end state, but a charter should not assume it.

Open question: **who owns "what changed"?** The eval layer produces a full tape every tick; the renderer must diff old-tape → new-tape (by identity, O(changes)) and emit buffer patches. P11 makes identity do this work for free — no graph, same trick as the pick AABB cache.

## What TypeGPU gives us (from the official skill, targeting typegpu 0.12)

- `d.*` schemas: one definition for GPU layout, CPU buffer, and TS type. Node instance structs fit this directly.
- `'use gpu'` TS functions transpiled to WGSL by `unplugin-typegpu` — shaders written in TS with real type inference. This matches the code-first ethos: user scenes are TS programs; render stages stay TS too.
- `root.createMutable(...)` fixed resources: shaders read scene data without manual bind groups.
- Guarded compute pipelines + storage textures if the SDF bake route (compute pass rasterizing the distance field, fragment pass just samples) wins the spike.
- `@typegpu/sdf` ships `sdLine`, `sdDisk`, `sdRoundedBox2d`, AA masking patterns — the 2D primitives are already there.

### `@typegpu/geometry` — unpublished, but decisive (source at `/root/typegpu`)

TypeGPU cloned parallel to this repo (`/root/typegpu`, branch main). `packages/typegpu-geometry` is `private: true` (0.11.0, unpublished) and contains exactly the stroke primitive layer this prototype would otherwise have to write:

- **`polylineVariableWidth(A, B, C, D, vertexIndex, MAX_JOIN_COUNT)`** — variable-width polyline segments generated *in the vertex shader* from control points `{position: vec2f, radius: f32}`. Neighboring points A/D feed join geometry; interior segment BC is drawn per instance. Joins (`miter`, `round`) and caps (`butt`, `square`, `triangle`, `wedge`, `arrow`) are injectable via `tgpu.slot`s (`joinSlot`, `startCapSlot`, `endCapSlot`) — filled with `root.with(slot, fn)` at pipeline creation.
- **`lineSegmentIndices(MAX_JOIN_COUNT)`** — shared index buffer (u16); join vertices address dynamically via `coreVertexIndex = (vertexIndex - 2) & 0b11`, so join resolution is a uniform choice, not a re-triangulation.
- **`circle(vertexIndex)` + `circleVertexCount(subdivLevel)`** — max-area circle subdivision (humus.name trick): unit vector per vertex, no geometry uploads, quality scales by level.
- Single draw call per pass, MSAA x4 for AA, alpha blend; the `lines-combinations` docs example (`apps/typegpu-docs/src/examples/geometry/lines-combinations`) is the reference integration: control points in a slot-bound storage array, one instance per segment, `outPos = vec4f(position * w, 0, w)` homogeneous trick, `lineSegmentLeftIndices` for the no-overlap "half" variant.

Implication for oblik: segments, circles, and point marks (disk + capsule = point-with-radius) map straight onto this; what remains ours is **fills** (region/csg2) — the SDF-vs-tessellation question in the spike — plus the tape→buffer adapter and camera uniform. The `w` homogeneous output also suggests screen-space-consistent widths (hairlines at zoom) are already solved for in the geometry package's model: radius is in world units, `w = 1/radius` feeds the projection.

Design notes from the author of the library:

- **Closed loops need no library change**: render one more segment whose instance indices wrap modulo back to the buffer's first point — the wrap join falls out of the normal neighbor-driven join logic.
- **Circles and arcs skip the library entirely**: their vertex expansion is analytical (`circle(vertexIndex)` style). A stroked circle is just two analytic triangulations at `r ± width/2`; arcs are the same with a start/sweep angle. Arc-length for the ghost's dashed stroke comes free from the angle parameter — no per-vertex arc-length plumbing needed for these.
- **Selection outline/knockout chrome is a candidate for jump flooding** (`createJumpFlood` in `@typegpu/sdf`): rasterize the pane's geometry to an offscreen texture, flood the pixel-space signed distance field, and derive the outline (7px) and knockout (4px) bands from that field instead of re-stroking geometry. Chrome metrics are defined in pixel space, and the field is pixel-space by construction — this sidesteps per-shape stroke geometry entirely, including for CSG shapes whose outline would otherwise mean stroking every loop of the boolean result.

## Environment questions

- WebGPU in the demo's browsers: Chrome/Edge fine; Safari/Firefox status to verify. Headless chromium (Playwright rig) needs `--enable-unsafe-webgpu` / SwiftShader fallback — must confirm the test rig can render or we test logic headless and pixels by eye.
- Fallback story when `navigator.gpu` is absent: SVG renderer takes over for the same scene? Or the scene kind is simply unavailable? (Parallel-kind framing suggests: unavailable, with a clean error.)

## Locked (candidates, not yet locked)

Nothing is locked yet. Candidate locks, borrowed from the parallel-kind decision and P11 experience:

- One `TgpuRoot` for the app lifetime, created lazily on first `euclid2-typegpu` pane; `root.destroy()` on HMR of the renderer itself, never per-eval.
- Camera lives in one uniform written per frame; node data lives in storage buffers written per tick (patch, not rewrite, where identity survives).
- SVG HUD unchanged: point marks, handles, sliders, selection chrome stay DOM/SVG — the GPU pass draws world geometry only. Hit-testing stays CPU-side (P11 AABBs), at least for this cut.
- The eval layer must not know the renderer exists: no GPU types in `eval/*`, no renderer-owned fields in trace nodes. The adapter maps tape → GPU state.

## Open questions for the spike

1. SDF vs triangles for filled polygons: at what vertex count does the per-pixel polygon SDF lose to CPU tessellation?
2. Can the csg2 tree evaluate *directly in-shader* (tree of SDF ops in a storage buffer, interpreted by the fragment shader), and does that kill `evaluateRegions`/tessellation for the GPU scene kind?
3. Buffer update strategy: how much of a tick's upload is a patch vs a rewrite in practice (bead drag in cache-lab should be: one instance slot)?
4. Line dashes, variable stroke width in screen space, and zoom-dependent hairlines — the things SVG gave us free that SDF makes us write by hand.
5. Text rendering (labels, slider values) — SVG HUD keeps this; is anything world-space textual?

## Not this prototype

- 3D scenes, cameras with perspective, depth — the 3D move comes after this renderer proves lifecycle, upload, and picking.
- Replacing the SVG renderer or touching its code paths beyond registering the new scene kind.
- GPU-side picking, GPU particles, post-processing, shadows.
- Changing the eval layer, site memoization, or user `memo()`.
