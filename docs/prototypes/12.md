# Prototype 12 — a WebGPU 2D canvas renderer (`euclid2-typegpu`), and the end of the SVG view

**Status:** shipped; this record closes it. The render half is proven on the GPU: grid/axis hairlines are an analytic instanced pass (CPU writes one `GridSpan` uniform per view; the vertex shader expands every hairline quad), fills are analytic winding walks inside per-island AABB quads, strokes and circles are instanced analytic geometry, all at 4× MSAA on one color attachment.

The interaction half shipped too: CPU picking with click cycling, edit drags that write literals, the placement tools with ghost previews and snap markers, and HTML bind labels (pixel-verified against the SVG view while it still existed). And the prototype ended further than its charter aimed — **the SVG view is gone** (`dfc1b86`), so `TypegpuView` is not an alternative implementation any more, it is the euclid2 renderer. The contract it reproduces now lives in `docs/chrome.md` and the shared `euclid2/view/` modules rather than in a sibling rasterizer. Open items are in the checklist and the capability survey below.

The reference behavior was not invented here: it was the SVG view's contract (`packages/oblik/src/euclid2/`, `docs/chrome.md`), stated in pipeline terms so the WebGPU view could reproduce it feature-for-feature before the SVG view was deleted. **Scope was full replication of that interaction and chrome; implementation order was ours to decide.**

## Went well

**The unit rule paid for itself everywhere.** "Every look knob is logical CSS px; `dpr` enters only at the canvas and the world→NDC mapping" turned zoom into a frame-uniform write and nothing else — no record depends on the zoom, so a 48 → 48.5 step rewrites zero records where baking `px / scale` in rewrote 226 of one scene's 288. It is the reason a drag tick and a camera move are both cheap.

**The whole chromatic result came out of one distance the fill pass already had.** The fill shader evaluated the signed distance to its nearest boundary for the AA ramp anyway, so an inner stroke is a band of `-d` and a hot halo is the next band — silhouettes, round joins, hole boundaries and rounded offsets all fall out of the field, with no restroke, no clip mask, and no extra buffer, order array or record slot. `halo.ts` is shared by the span fragments and every compiled shape's pair.

**Compiling the tree made leaf numbers data.** A `csg2`/`region` fill becomes a shape-keyed field whose WGSL depends on the tree's shape only: 26 CSG fills across the demo scenes compile to nine artifacts, and nudging every number in a drag leaves the WGSL byte-identical, so a drag can only rewrite data. Colour and alpha live in the quad, so hover and selection recolor through the same byte diff as the fill.

**Identity-stable nodes made GPU resources keyable.** P11's memo returns the previous eval's value object, so the adapter keys buffers on node identity and byte-diffs patches: a node keeps its slot until it dies. This is the property the prototype existed to exploit, and it held.

**The record split was free.** Segments and arcs live in separate arrays with their own windows, so the segment loop — the loop a 350-span gear face spends its time in — reads half the bytes and contains no carrier branch at all. Winding is a sum and `dmin` a `min`, so order is irrelevant on both sides and the split cannot change a pixel.

**Chrome metrics are data, not shader structure.** Points ride `@typegpu/geometry` disks; text is HTML (bind labels, slider HUD, palette prompts), which is why labels follow the camera by compositing a `transform` rather than by laying out per frame.

## Needs improvement

**A triangulation rewrite was tried and dropped.** Branch `p12` (commit `329ddea`) replaced the winding-fill shader with CPU earcut triangulation: flat `FillTri` instances, the `FillEdge`/`FillRegion` schemas and the per-pixel shader deleted. It never merged — it sits one commit off a base 20 commits behind `main` — and `main` took the distance-band direction instead. The reason is structural and worth keeping: flat triangle lists cannot carry the boundary-band outline or halo (there is no distance left in the fragment) and cannot express a compiled field at all. Anyone tempted to re-propose earcut should read that commit first.

**The polygon span walk is still O(edges × pixels)** and is the one place the fill model is not obviously right. Compiling a tree does not help it; the record split only halved the bytes it reads. The walk itself is unbenchmarked against its original standard — which is now deleted along with the SVG view.

**Chrome text never arrived.** The checklist still carries it as missing, and it is the last SVG behavior without a pipeline story. HTML covers labels and the HUD; it does not cover text that has to be clipped or measured against geometry.

**Region and trace ghosts still have known deltas:** the partial chain closes back to the start vertex with a straight segment, trace-ghost region fills are ink-only, and a round ghost dot coincident with the crossing diamond is suppressed because the diamond's inradius is under the dot's radius.

**The `view/` directory is misnamed.** What is left of it is contract and shared logic (`marks.ts`, `chrome.ts`, `pointer.ts`, the HTML HUD) plus three chrome components the figure view also paints through. That rename is parked in the refactoring plan and should not be mistaken for dead SVG code.

## Pass / fail

**Passed.** Grid and axes at 1 CSS px on retina and standard displays; translucent fills at .16/.28 over paper and grid; ink always above fills by draw order, never depth; hover and selection halos under the paint, reading ring → paper gap → paint; halos suppressed while dragging; fills as distance bands with the outline flush against the silhouette (round joins, holes, rounded offsets all in-field); a compiled field byte-identical under a data-only drag; 26 CSG fills compiling to nine artifacts across the demo set; identity-keyed pools with byte-diffed patches that skip a node which does not fit rather than corrupting the pool; CPU picking with the shared `pick.ts` ranks and CSS-px tolerances, cycling on a repeated completed click; placement tools with ghosts, snap markers and scope muting; HTML bind labels matching the SVG view pixel-for-pixel before it was deleted; repeated cells — `polarRepeat` folds the query point into the nearest copy and evaluates one cell, so a 40-tooth ring costs one tooth per pixel and its record holds one tooth's spans, with the hub union closing the cell's own interior seams; the fold pinned against the CPU reference, its three preconditions pinned by `geom/repeat.test.ts`; the SVG view and the `SVG | GPU` switch deleted, with the pane mounting `TypegpuView` directly.

**Fail would have been:** a second renderer or a capability switch; depth or stencil ordering for translucent fills; a GPU pick target; re-resolving a fill tree per frame; a halo that restrokes the boundary or masks it with a clip; a record that depends on the zoom; `px / scale` baked into a record or `dpr` multiplied into a knob; text rendered as GPU glyphs; a scene kind named after the renderer.

## Why a renderer, and why now

The SVG renderer rasterized with the browser: every fill was a tessellated path, every stroke a `<path>` re-updated on camera moves, and zooming past a few thousand nodes hit SVG serialization and re-layout costs that no eval-layer caching could touch. In 3D none of this exists as an option — GPU rendering is the only path. Proving the 2D canvas on the GPU was the smallest step that derisks the machinery we need everywhere: device/root lifecycle under Solid, per-tick buffer writes from eval output, camera as a uniform, picking under a GPU renderer.

**The P11 connection:** trace nodes are identity-stable across draft ticks (memo hits replay the previous eval's value objects). That means the renderer can key GPU resources on node identity — a node keeps its buffer slot until it dies, and a drag tick writes one new slot instead of re-uploading the world. This is the property the whole prototype is built to exploit.

## The behavior contract

### One renderer

There is **no `euclid2-typegpu` scene kind** and no renderer switch. `Host` branches only on `figure` vs `euclid2` — `eval/scene.ts` has exactly those two kinds — and every `euclid2` scene is rendered by `TypegpuView`, which the euclid2 pane imports directly (`euclid2/Pane.tsx`). The pane owns eval, selection, drafts, hover, tools and the slider HUD exactly once.

The former **SVG view** (`Euclid2View`, `euclid2/view/View.tsx`), the `<Dynamic component={gpu ? TypegpuView : Euclid2View}>` swap, the per-scene `SVG | GPU` chip and its stored per-file setting were all deleted in `dfc1b86`. What survives under `euclid2/view/` is shared logic the GPU view calls — `marks.ts`, `chrome.ts`, `pointer.ts`, `chrome-metrics.ts`, the `SliderDock` HTML HUD — plus the chrome pieces the **figure** view still paints through (`ChromeBand`, `FillFace`, `RegionInk`, `ChromeClip`). None of it is a second rasterizer, and none of it is dead SVG code to delete.

Consequences: a scene is a single file with no `typegpu-*` twin, there is no renderer-aware eval layer, and `navigator.gpu` absence has no fallback renderer — the view shows its own "WebGPU unavailable" notice.

### Scene model

The scene is a **tape** (`trace: TraceNode[]`), not a shape tree. Both view implementations receive the same evaluated, memoized, identity-stable nodes, each with `id`, `occ`, `bind`, `editable`, `kind`, `value`; `traceKey = id:occ`. Geometry kinds: `point`, `glider` (on segment/line/circle carriers), `segment`, `line`, `parallelLine`, `circle`, `polygon`, `region`, `csg2`/`pick`/`polarRepeat`, `slider`. Selection, hover, chrome, drags, and snapping all refer to trace nodes, and a hot node is named by its full trace key (`id:occ`) rather than a bare `id` — hover lights up one occurrence of a repeated node, never every copy; every node that draws is a potential pick target. There is **no separate "shape" object at the chrome level** — a `region(...)`/`csg2(...)` node is one selectable node.

### Paint model (colors, alphas, pass order)

- Draw order per band: **fills, then ink (strokes/circles), then points**. An item lifts only within its band: idle siblings paint → hover overlay + hover paint → selected overlay + selected paint (`splitChrome`, `chromePasses` in `view/marks.ts`).
- **Hover and selection are halos under the geometry** (`docs/chrome.md`): the ring is a wider stroke _under_ the paint; paint covers the halo's center. The overlay is two layers when selected — `outline` (ring color) then `knockout` (paper color) on top of it — so it reads ring → paper gap → paint. Hover overlay is outline only, no knockout.
- **Halos are suppressed while dragging** (overlay passes skipped; lifted paint stays).
- Colors are CSS vars resolved once per theme: `--oblik-ink` (idle), `--oblik-accent` (editable, not hot), `--oblik-selected-paint` (**hover and selected share white/cream**), `--oblik-ring`, `--oblik-knockout` (paper). Muted = opacity 0.32. Fill alpha 0.16 idle, 0.28 hot.
- Chrome metrics (CSS px, defaults in `view/chrome.ts` `DEFAULT_CHROME_METRICS`): construction paint width **1.5**; ring `outlinePx` **7** (hover opacity 0.5, selected 1.0); `knockoutPx` **4**; points get wider halos — `pointOutlinePx` **14**, `pointKnockoutPx` **9**; point discs: derived **r 3.5**, editable **r 5**, paper outline stroke **2**; invisible hit target `HANDLE_R` **7**; snap radius `SNAP_R` **9**.

### Point marks and "handles" (there are no bbox grips)

Every point/glider node is **always visible** as a small disc (ink fill, paper outline; accent when editable; white when hot; bind label beside it when named). A `Handle` in `view/Hud.tsx` is an _invisible_ r=7 hit circle over editable points for placement-tool DOM snapping — not a visible grip. **"Drag handles write literals"** (pane status line) means: grab an _editable_ geometry node and drag, and its literal values are patched back to source (draft → commit):

| grabbable node                 | drag                 | written literal(s)          |
| ------------------------------ | -------------------- | --------------------------- |
| `point`                        | move                 | `[x, y]`                    |
| `glider` (segment/line/circle) | along carrier        | `t`, `s`, or `[ux, uy]`     |
| `circle`                       | rim (radius)         | radius, min 0.05            |
| `parallelLine`                 | perpendicular offset | distance off base line      |
| offset `csg2`                  | perpendicular offset | offset distance along stock |
| `slider`                       | HUD                  | scalar value                |

Segments/lines/circles are _not_ grabbable — clicking one selects it. Click-vs-drag is decided at release by travel ≥ **4 CSS px** (`PICK_CLICK_PX`); dead zones 2 px (edit) / 1 px (pan). Releases commit drafts and select via `onPick`.

### Placement tools, snapping, scopes

Space opens the tool palette; tools place geometry in steps with typed-arg prompts (Tab/Enter/Escape), ghost previews (dashed ink, ghost fill, offset arrow), and snap markers (circle for plain snaps, diamond at crossings). Snap targets: named points/gliders (`snapBoundPoint`), strokes/circles for glider placement (`snapStrokeCarrier`), sliders as length references. Scope focus (`select is scope`) restricts eligible snap carriers and mutes the rest.

## The pipeline model

### Picking model — pure CPU, reuse `euclid2/pick.ts` verbatim

Picking is **CPU geometry over the trace**, exactly the function the SVG view calls (`hitsNear` → `hitTest`), with no DOM dependency:

- **Rank order** (the "point beats line beats region" rule, already encoded): 0 point/glider → 1 segment/line/parallelLine/circle → 2 csg2/pick/polarRepeat → 3 region/polygon; then nearest distance; ties to the **later-defined node** (deterministic "on top").
- **Tolerances in CSS px**: geometry `GEOM_PX` 8, points `POINT_PX` 12; world radius = `px / scale` (SCALE_MIN 8 makes the guard harmless). Inside a fill (`d === 0`) always counts. AABB prefilter cached per node identity (P11's WeakMap).
- **No GPU pick target.** Rejected for three compounding reasons: MSAA resolve **averages** samples, so an ID attachment resolved from a hairline (2 of 4 samples covered) is garbage and WebGPU offers no "any-sample-wrote" resolve; pick geometry would diverge from visible geometry (fat bodies vs cores); and hover needs a result every pointer move — at today's node counts a CPU linear scan is free, while a GPU pick pass would need demand re-renders plus async readback plus throttling. The SVG view already _is_ CPU picking; full replication means reusing it. GPU instance-ID picking stays parked as the 3D rehearsal when 3D begins.
- **Body-pickable strokes**: a stroke is pickable when `dist(click, centerline) ≤ max(visual half-width, pickbox)` — the fat body is grabbable, hairlines always keep the pickbox floor. Same formula the GPU probe would have used, without a probe.
- **Cycling (new — SVG had none):** `onPick` receives the full ranked `hitsNear` list, not `hits[0]`. A **completed click** (down+up within the click dead zone — a click, not a bare pointer-up) whose top hit is the _already-selected_ node advances through the list; the next click on a different top hit resets to that node. Fills beneath strokes are already in the ranked list, so cycling reaches under.

### Render model — one ordered color target, chrome as extra draws

- Single color attachment, 4× MSAA, painter order: paper clear → grid/axes (instanced analytic hairline quads; axes recorded after the grid so they land on top, still under world ink) → **fills** → **ink** (strokes, then circles) → **points/chrome**. Translucent fills blend over paper/grid; ink always renders above fills — guaranteed by draw order, never depth. Chrome band passes interleave _within_ each band in the SVG order (idle paint, hover overlay, hover paint, selected overlay, selected paint) so halos land above lower bands and, for ink, under their own paint; while dragging, overlay passes are skipped. Fills are the exception in one direction only: their halo is opaque and knocks the fill out, so it is drawn **after** its own paint.
- The `Frame` uniform already carries the chrome metrics and dash pattern (`outlinePx`, `knockoutPx`, `dash`, `dpr`); `RUN_DASHED` + `Frame.dash` exist for ghost previews and future dashed strokes.
- Fills come in two flavours, both analytic per pixel inside an AABB quad, and the adapter routes each node: **span fills** (analytic winding over a span array — polygons, picks, tool ghosts) and **compiled fields** (`csg2` and `region` nodes — see below).
- **A fill's outline and its hot halo are bands of its own boundary distance.** Every fill carries the SVG `inkClass` stroke at the construction width (ink, accent while editable, cream while hot), **centred on the boundary** like that stroke so it lines up with the edge that defined the region rather than doubling it inside; a hot fill adds the halo band — measured inside from the edge — over it. No restroking and no clip mask: the pass already evaluates the signed distance to the nearest boundary (`d`, negative inside) for the analytic AA ramp, so an inner stroke is a band of `-d` — `(0 .. outlinePx/2)` in the ring color and, when selected, the next `knockoutPx/2` in paper. The outline therefore sits flush against the silhouette, round joins / hole boundaries / rounded offsets all fall out of the field, and the band is **opaque and paper-backed**: the ring reads as a clean 50% accent on hover and a solid one when selected, never as accent under the fill's cream paint. Two layers of one quad — a `paint` run then the node's `halo` run, same record slot, two fragments — so the halo costs no extra buffer, order array or record; `FieldQuad`/`FillRegion` carry the band's colors, opacities and widths as data, which also means a hover recolors the halo through the same byte diff as the fill — and since those widths are CSS px rather than world units, a zoom recolors and rewrites nothing at all.
  - Deviation from the SVG view, deliberate: SVG strokes the region path and clips it to the **outside** of the fill, _under_ the paint. Inside-and-over keeps the ring off the grid and neighbouring geometry and preserves its strength at the cost of saturating on shapes thinner than the band. `docs/chrome.md` records both.
  - `gpu/pipelines/halo.ts` owns the band and outline math, shared by the span fragments and by every compiled shape's pair; `halo.test.ts` pins the pixel semantics on the CPU (with a dense profile sweep asserting no step anywhere in the stack), `wgsl.test.ts` pins the structure, and the per-shape pipeline cache is keyed on shape + **layer**.
  - Chrome inside one fragment is composited as **areas of one pixel**, not as stacked blends: the color and the alpha are both area-weighted by the two coverages. The naive version (choosing a layer's color from its own coverage) cancels the ramp and steps hard at the knockout→ring seam — the reported bug, now regression-tested.
- **A span is either a segment or an arc, and they live in separate arrays.** `fillSpans.ts` splits every boundary walk into `segs` (`a`,`b` — 16 B on the GPU) and `arcs` (the same plus `center`,`radius`,`span`), each with its own window (`segOffset`/`segCount`, `arcOffset`/`arcCount`) on the region or leaf record. Order is irrelevant on both sides (winding is a sum, `dmin` a `min`), so the split is free — and it is a pure win where it counts: the segment loop reads half the bytes and contains no carrier branch at all, which is the whole cost of a sampled polygon boundary (a gear face is ~350 segments and one arc). The arc loop keeps `atan2`/`sqrt` behind its own window, and a bounds helper per kind keeps the AABB padding exact. Both shaders are byte-checked for this: `gpu/pipelines/wgsl.test.ts` and `field/wgsl.test.ts` slice the emitted WGSL at `fillSegs[`…`fillArcs[` and assert the segment loop mentions no `atan2`, `sqrt`, `radius` or `center`.
- **Compiled CSG fields** (`gpu/field/`). A `csg2` tree whose operands are all single scalar fields is compiled instead of resolved: `plan.ts` walks the retained operand tree (`Csg2 = { op, of }`; leaves `spans | circle | halfPlane | offset | repeat`, where a `region` operand contributes its `spans`) into a **shape** string, a leaf list addressed by comptime index, and a superset AABB; `assemble.ts` turns that shape into straight-line TGSL — ops fold pairwise into `min` / `max` / `max(a, −b)`, an offset is `child − d` (round joins fall out of the SDF shift, like `roundOffsetValue`), a `region` leaf inlines the same winding + nearest-boundary walk the span pass runs. Leaf reads are `fieldLeaves[base + <literal>]`, so the window base is the only runtime value. Consequences: **no island resolution on the CPU for trees** (the field is the union directly, one quad per node), exact arcs (no chord approximation), and — the property the cache rests on — **leaf numbers never reach the shader**: nudging every number leaves the WGSL byte-identical, so a drag can only rewrite data.
  - Reuse is keyed on the shape: 26 CSG fills across the demo scenes compile to **9 artifacts**, and a node's colour/alpha live in its quad, so hover/selection recolor without touching the shader either. A `pick` (island-restricted) and a `polygon` (not a `CsgOperand`) stay on the span pass by design.
  - Fills are translucent, so paint order matters and two pipelines cannot be merged into one draw: the adapter emits a **draw run per node** in band order (`FillDraw`) and the painter plays them back to back, using `firstInstance` to start each run in that pass's shared order array. One draw per fill node per layer (paint, then halo when hot), exact SVG compositing order.
  - Pools are identity-keyed and byte-diffed like every other buffer, one per record kind: quads `MAX_FIELD_QUADS` 512, leaf records `MAX_FIELD_LEAVES` 4096, and the field's spans — `MAX_FIELD_SEGS` 8192 segments + `MAX_FIELD_ARCS` 2048 arcs, which is 192 KB against the 256 KB the old combined record took. The span-pass pools (`MAX_FILL_SEGS` 8192 + `MAX_FILL_ARCS` 1024) likewise hold double the old segment capacity for less memory than before, and they carry the region load the field pools do not. A node that does not fit is skipped, the same failure mode as ever; `fillSpans.test.ts` measures the whole demo set against both pools so the caps cannot drift silently (currently ~3.0 k span segments / ~0.4 k field spans).
  - Tested without a device: `plan.test.ts` checks the TS twin of the shader against the CPU reference (`operandSdf`/`csgSdf`) on 12,690 probes — agreement to 1.3e-15 — and `wgsl.test.ts` resolves each shape through `tgpu.resolve` to assert the folded structure, the literal leaf offsets, the absence of op dispatch, and the byte-identical-under-data guarantee.
  - **`polarRepeat` folds in the field; it never expands.** A repeat is unmarked (like `along` / `dist` / `diff`): it is an operand, not a tape node, so `csg2(...)` is what draws it. `polarRepeat(cell, count, about, rotation?)` means `count` copies of one authored, unrotated cell, `2π/count` apart about `about`, spun by `rotation`. The compiled field inlines the **fold**: `assemble.ts` maps the query point into the nearest copy's frame and evaluates the cell once there, so a 40-tooth ring costs one tooth per pixel and its record holds one tooth's spans. The repeat's numbers (`count`, `rotation`, the axis) are leaf data like any other, so nudging them rewrites no WGSL; `repeatAabb`/`repeatBox` bound the quad by unioning every rotated corner of the cell's box (above a copy threshold the box is the disc through it). Two consequences, both from `7.md`: the cell index is measured **from `rotation`**, not from the angle, so a fold that forgets the subtraction renders the ring at `rotation = 0` and nowhere else; and because the field is one cell's distance, a cell that tiles the plane has its own seams as internal boundary — which is why the fill unions in the **hub** disc the cells stand on. The geometry side keeps the opposite view: `evaluate-regions.ts` stamps real rotated copies (`rotateRegion`) for island queries and span-pass fallbacks, which is what a rasterizer that would rather scan 40 polygons than evaluate a field needs. `geom/repeat.test.ts` pins the three preconditions (cell centred on its sector, inside it, not straddling the axis); `field/plan.test.ts` runs the fold against the CPU reference; `field/wgsl.test.ts` asserts the folded structure is what was emitted.
    (`circle` + `circleVertexCount`, `gpu/pipelines/disks.ts`), emitted as concentric layers per mark replicating the SVG `PointMark`: paint disc at mark radius, the always-on paper rim just outside it, and halo ring/knockout discs _beneath_ the paint — the halo covers earlier bands but never the point's own paint. Points ride the adapter feed with the other drawn nodes.
- Handles, sliders, bind labels, palette prompts, and all **text is HTML** — in the WebGPU view text is an HTML overlay on the canvas, not GPU glyphs and not SVG (SVG is too limiting for chrome text: no padding, etc.). World-anchored text (bind labels) is positioned per frame from the same world→screen mapping (`worldToScreen`, CSS px); sliders/HUD are HTML controls. Geometric chrome that needs no text (ring/knockout, snap markers, ghost, point halos) stays GPU geometry.
- **Bind labels** (`euclid2-typegpu/BindLabels.tsx`): one `<span>` per named point/glider — exactly the SVG point band minus its overlay passes (`isBindLabelNode`) — inside a pointer-transparent layer that copies the paper box. Position is `worldToScreen(anchor) + (10, −8)` (the SVG `<text x/y>`), lifted by the line-box height because SVG's `y` is a baseline and HTML positions a line box by its top; the shift rides `transform`, so a camera move only recomposites. Camera/pane are reactive props, so labels follow the painter tick. Muting matches `PointChrome` (`mutePoints`, or out-of-scope, and never while hot/selected). Because the layer is HTML it paints **above all GPU geometry** (SVG draws labels inside the point band), and it is hidden until the first frame lands. The offset/color/size contract lives in `docs/chrome.md`; the two views were compared side by side and match.
- **Ghost previews**: dashed strokes via `RUN_DASHED`, translucent ghost fill via the fill pipeline, arrowheads already exist in the vendored cap set. Snap markers are GPU geometry (circle for a plain snap, rotated square for a crossing) — they carry no text, so nothing about them wants HTML.

### Units model — DPR-sensitive, every look knob in logical px

**Rule: all look-knob constants are logical (CSS) px.** The only place `dpr` appears is the canvas backing size and the world→NDC mapping; it is **never** multiplied into a knob, and the NDC mapping must never be changed to compensate for a knob. Concretely: `size`/`pane` stay CSS px, the canvas is `size × dpr` device px, `Frame.dpr` rides along for anything genuinely pixel-sized (e.g. `fwidth` AA), and every knob converts to world units once as `px / scale`. Result: a 1 CSS px hairline covers `dpr` device px at any zoom, identical on retina and standard displays — which is what the SVG `vector-effect: non-scaling-stroke` + CSS-px widths already deliver and what the GPU must match. Audit target: the grid hairline (must be **1 CSS px**; verify `grid.ts` against this rule) and every chrome stroke/annulus/disc radius above.

**Where that `px / scale` conversion happens matters.** The records store widths in **px** and the shaders convert with `worldPerPx(frame.scale)` (`gpu/frame.ts`), one call per use — `radiusPx`, `halfPx`, `edgeWidthPx`, `haloHalfPx`, plus `MarkerInst`'s px extents, which is where the unit came from. Baking `px / scale` into the record instead makes the camera a _record_ input: a 48 → 48.5 zoom step rewrote 226 of the Fillet scene's 288 records (every stroke radius, circle annulus, disc radius, fill outline and halo band), where in px it rewrites **none** — a zoom becomes another frame-uniform write like a pan. Two consequences worth knowing: the fan's piece count for a circle/arc is derived in the vertex shader (sweep × radius × scale, clamped to `MAX_CIRCLE_PIECES`) rather than baked, and the quad AA skirt is applied in the vertex shader (`QUAD_PAD_PX`) so the stored AABB stays pure world geometry. The one width-shaped thing that still follows the camera is an **unbounded field box** (a half-plane has no world extent of its own), which is clamped to the pane — the only record a pan or zoom may legitimately rewrite.

Known deltas in the ghost layer: the region preview closes its partial chain back to the start vertex with a straight segment (the SVG path closes the same way, but arc edges are approximated in the chain's shoelace orientation test); trace-ghost region fills are not drawn yet (ink only); and a round ghost dot coincident with the crossing diamond is suppressed — the small diamond's inradius (SNAP_DIAMOND_R/√2 ≈ 3.5px) is under the 4px ghost dot radius, so the two together read as a circle.

The renderer must not change eval or pick semantics: identical trace in, identical interaction out, different raster. With the SVG view deleted, that contract is the shared `view/` logic plus `docs/chrome.md` — there is no longer a sibling implementation to diff against.

## GPU capability survey — what the renderer is not using yet

The GPU surface actually in use is **one color attachment at 4× MSAA**: no depth, no stencil, no compute, no offscreen color target (capture resolve aside). Hover/selection chrome is CPU-chosen band recolor plus chrome geometry strokes (disc layers and the fills' boundary bands shipped) — deliberately, per the models above.

**Design decision — translucency gates only the occlusion-family tricks.** World fills stay translucent (alpha over paper/grid); ink edges always render above fills. Ordering is painter order, never depth. Stencil is _color-agnostic_: stencil-then-cover fills and clip masks work unchanged for translucent fills. What translucency precludes is expressing _overlap between separate shapes_ with masks: a stencil test is binary keep/kill before blending, so masks are set semantics (one shape owns the pixel), while translucent overlap needs both shapes to contribute — ordered alpha blending only. Depth ordering and stencil-encoded cross-node subtraction stay out while fills blend.

- **Depth buffer.** Additive on installed typegpu 0.12.5; would buy draw-order freedom and 3D plumbing rehearsal but breaks translucent compositing (unsorted alpha). Revisit when an opaque pass exists or 3D starts.
- **Stencil buffer** (Skia GPU backend / NV_path_rendering territory): _stencil-then-cover fills_ (even-odd parity, O(1) fragment cost, AA from MSAA) is the standing benchmark vs the analytic winding fill; _clip masks_ (stencil `equal` while stroking) would replace CPU clip-geometry surgery. Stencil-CSG _subtraction between separate nodes_ is mask-encoded occlusion — wrong compositing for translucent overlap, not because stencil needs opaque colors.
- **GPU picking.** Revisited and **not adopted** (see Picking model): CPU `hitsNear` is the SVG behavior, free at today's counts; MSAA resolve averaging corrupts any resolved ID attachment. Parked as the 3D picking rehearsal.
- **GPU-native selection chrome.** Adopted as the plan above: no new pipeline — the selected node's resolved loops re-stroked at px widths (segments → stroke instances, arcs/circles → annulus instances), points as disk + ring bands. Jump-flood (`@typegpu/sdf`) stays in reserve for deep-CSG silhouettes / mass selection.
- **Offscreen layers / pixel caching**: fights the thesis (re-rasterization is cheap; camera moves invalidate caches). Scale play for 10⁵+ nodes; not this prototype.
- **Compute**: (1) _grid hairlines_ — done as an analytic instanced pass, not compute; (2) _dashes_ — `RUN_DASHED` + `Frame.dash` reserved but dead; arc dashes are analytic from the sweep angle; (3) _jump-flood chrome_ in reserve.
- **OIT, drawIndirect, occlusion/timestamp queries**: real but later; only timestamp queries serve the fills benchmark now.

## Environment questions

- WebGPU in the demo's browsers: Chrome/Edge fine; Safari/Firefox status to verify. Headless chromium (Playwright rig) needs `--enable-unsafe-webgpu` / SwiftShader fallback — confirm the rig can render, or test logic headless and pixels by eye.
- Fallback when `navigator.gpu` is absent: there is no fallback renderer any more. The view's init reports "WebGPU unavailable" and the paper stays blank, so Safari/Firefox WebGPU support is the open question rather than a switch to flip.

## Locked

- One `TgpuRoot` for the app lifetime, created lazily on first `TypegpuView` mount; destroyed on HMR of the renderer, never per-eval.
- **One renderer, no switch.** The euclid2 pane mounts `TypegpuView` directly; the SVG view, the `Dynamic` swap, the per-scene `SVG | GPU` chip and its stored setting are deleted. Scene kinds stay `figure` vs `euclid2`, and eval never learns that a renderer exists.
- Camera + pane + chrome metrics live in the `Frame` uniform (one write per view sync); node data lives in storage buffers written per tick as byte-diffed patches keyed on node identity (P11). Grid: one `GridSpan` uniform per sync.
- **Picking is CPU** — the shared `euclid2/pick.ts` runs in the WebGPU view unchanged: same ranks, same CSS-px tolerances, same AABB prefilter, body-pickable rule. **No GPU pick target.**
- **Cycling** on repeated completed clicks advances the ranked candidate list (new behavior, not present in SVG).
- **Fill trees compile; they do not re-resolve per frame.** A `csg2`/`region` fill becomes a shape-keyed field whose WGSL depends on the tree's shape only — leaf numbers, colour and alpha are data. Rebuilds happen on a **shape change** (an operand added/removed, an op changed, a leaf kind changed) and nowhere else; the pipeline cache is keyed on shape + target, and the fragment/WGSL is built once per shape. The CPU keeps `evaluateRegions` for picking and for the span-pass fallbacks (`polygon`, `pick`, tool ghosts) — never for a compiled field's pixels.
- **A fill boundary is stored as two arrays, not one union record**: straight segments (`a`,`b`) and arc carriers keep separate windows, so the segment loop never reads a carrier it cannot use. Both walks stay order-insensitive, so nothing about this can change a pixel — it only changes what the loop touches.
- **Chrome metrics and all look knobs are logical (CSS) px**; dpr enters only at canvas/NDC mapping, never into a knob. Grid hairline = 1 CSS px. Records carry the px values too, and the shaders do the one `px / scale` conversion, so no record depends on the zoom.
- **Text is HTML** (bind labels, slider HUD, chrome text) — never SVG or GPU glyphs in this prototype. Bind labels own a pointer-transparent layer over the canvas and follow the camera from `worldToScreen` (`BindLabels.tsx`); they therefore paint above all GPU geometry, where SVG draws them inside the point band.
- **Points/gliders render as GPU disks** through the `@typegpu/geometry` disk primitive (`disks.ts`) and are in the adapter feed.
- SVG HUD semantics are the contract (`view/marks.ts`, `view/chrome.ts`, `view/pointer.ts`, `pick.ts`); the WebGPU view reuses their logic and reproduces their pixels.
- The eval layer must not know the renderer exists: no GPU types in `eval/*`, no renderer-owned fields in trace nodes. The adapter maps tape → GPU state.

## Open questions for the spike

1. Stencil-then-cover fills vs the analytic winding fill: at what edge count and zoom does even-odd parity + MSAA beat the O(edges × pixels) walk? The live case is the **polygon** fill (a gear face: ~350 spans in one island, every covered pixel walking all of them) — compiling a tree does not help there. The record split (segment vs arc arrays) is done: the walk is now half the bytes and branch-free per record kind. What remains is the **walking**, not the reading: per-tile span binning built in a compute pass (the CPU stays out of it), a per-record AABB/run hierarchy traversed in the shader, or a scene-side samples knob. Nothing here is measured against the SVG view yet.
2. Buffer update strategy in practice: how much of a tick is a patch vs a rewrite (a bead drag in cache-lab should be one slot)?
3. Line dashes and variable screen-space widths — the things SVG gave free that the GPU must write by hand; `RUN_DASHED` + `Frame.dash` are the reserved seam.
4. Ring/knockout chrome for **ink** at high silhouette complexity: strokes/circles/points still restroke per loop, while fills answered the question by needing no restroke at all (the band is a clamp of the distance the fill pass already has). Does mass selection — many hot nodes, each a draw run per layer — push ink the same way, or does that end at jump-flood/hull chrome instead?
5. HTML overlay placement cost for world-anchored labels at high node counts (labels follow geometry each frame). Answer so far: one `<span>` per **named** point/glider, moved by `transform` only — a camera move is compositing, not layout, and the text matches the SVG view pixel-for-pixel; the SVG view pays the same text cost per frame inside the hud SVG. Untested beyond the demo scenes' node counts.

## Not this prototype

- 3D scenes, perspective cameras, depth — the 3D move comes after this renderer proves lifecycle, upload, picking, and chrome. GPU instance-ID picking returns with it as the rehearsal.
- Re-introducing a second rasterizer, a renderer capability switch, or a scene `kind` named after the renderer. The SVG view was deleted on purpose (`dfc1b86`); the shared `euclid2/view/` modules stay as contract, not as a fallback implementation.
- GPU particles, post-processing, shadows, offscreen pixel caching, OIT, drawIndirect.
- Changing the eval layer, site memoization, or user `memo()`.
- Text rendering on the GPU; SVG as a chrome/text layer for the WebGPU view (HTML replaces it).
