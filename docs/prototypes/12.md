# Prototype 12 — a WebGPU 2D canvas renderer (`euclid2-typegpu`), replicating the SVG view's behavior

**Status:** implementation + charter revision. The render half is proven on the GPU: grid/axis hairlines are an analytic instanced pass (CPU writes one `GridSpan` uniform per view; the vertex shader expands every hairline quad), fills are analytic winding walks inside per-island AABB quads, strokes and circles are instanced analytic geometry, all at 4× MSAA on one color attachment. What was still unspecified — and what this revision pins down — is the **interaction half**: what a scene renders, how picking works, and what hover/selection chrome is — as an explicit render/pick/chrome model that replicates the SVG view and the DPR rule for every pixel-space knob.

The interaction half has since **shipped**: the per-scene `SVG | GPU` switch, CPU picking with click cycling, edit drags that write literals, the placement tools with ghost previews and snap markers, and HTML bind labels (pixel-verified against the SVG view). What is still missing is listed in the checklist below — region halo restroke and chrome text.

The reference behavior is not invented here — it is the SVG view's existing contract (`packages/oblik/src/euclid2/`, `docs/chrome.md`). The charter's job is to state that contract in pipeline terms so the WebGPU view can reproduce it feature-for-feature. **Scope = full replication of the SVG view's interaction and chrome; implementation order is ours to decide.**

## Why a renderer, and why now

The SVG renderer rasterizes with the browser: every fill is a tessellated path, every stroke a `<path>` re-updated on camera moves, and zooming past a few thousand nodes hits SVG serialization and re-layout costs that no eval-layer caching can touch. In 3D none of this exists as an option — GPU rendering is the only path. Proving the 2D canvas on the GPU is the smallest step that derisks the machinery we will need everywhere: device/root lifecycle under Solid, per-tick buffer writes from eval output, camera as a uniform, picking under a GPU renderer.

**The P11 connection:** trace nodes are identity-stable across draft ticks (memo hits replay the previous eval's value objects). That means the renderer can key GPU resources on node identity — a node keeps its buffer slot until it dies, and a drag tick writes one new slot instead of re-uploading the world. This is the property the whole prototype is built to exploit.

## The behavior contract (SVG ground truth to replicate)

### Renderer switch — how the two implementations coexist

There is **no `euclid2-typegpu` scene kind**. `Host` branches only on `figure` vs `euclid2`; any `euclid2` scene is rendered by one of two interchangeable view implementations that share the same props contract:

- the **SVG view** (`Euclid2View`, `euclid2/view/View.tsx`) — the reference rasterizer;
- the **WebGPU view** (`TypegpuView`, `euclid2-typegpu/TypegpuView.tsx`) — this prototype.

The euclid2 pane (`Euclid2Pane`) chooses between them at runtime with `<Dynamic component={gpu ? TypegpuView : Euclid2View} …>`, so the pane owns eval, selection, drafts, hover, tools, and the slider HUD exactly once and they survive a renderer swap; only the view-local camera resets. A small `SVG | GPU` chip over the paper's top-right corner flips the choice; it is persisted **per scene file** (a stored signal keyed on the scene path) and defaults to **GPU**. There is deliberately no `navigator.gpu` capability check at the switch — when WebGPU init fails, `TypegpuView` shows its own "WebGPU unavailable" notice and the chip's SVG option is the fallback.

Consequences: no scene duplication (the former `typegpu-csg-tree.ts` / `typegpu-nested-circles.ts` twins are deleted — a scene is a single file, GPU or SVG per its stored choice), no renderer-aware eval layer, and both rasterizers consume the identical trace.

### Scene model

The scene is a **tape** (`trace: TraceNode[]`), not a shape tree. Both view implementations receive the same evaluated, memoized, identity-stable nodes, each with `id`, `occ`, `bind`, `editable`, `kind`, `value`; `traceKey = id:occ`. Geometry kinds: `point`, `glider` (on segment/line/circle carriers), `segment`, `line`, `parallelLine`, `circle`, `polygon`, `region`, `csg2`/`pick`, `slider`. Selection, hover, chrome, drags, and snapping all refer to trace nodes; every node that draws is a potential pick target. There is **no separate "shape" object at the chrome level** — a `region(...)`/`csg2(...)` node is one selectable node.

### Paint model (colors, alphas, pass order)

- Draw order per band: **fills, then ink (strokes/circles), then points**. An item lifts only within its band: idle siblings paint → hover overlay + hover paint → selected overlay + selected paint (`splitChrome`, `chromePasses` in `view/marks.ts`).
- **Hover and selection are halos under the geometry** (`docs/chrome.md`): the ring is a wider stroke _under_ the paint; paint covers the halo's center. The overlay is two layers when selected — `outline` (ring color) then `knockout` (paper color) on top of it — so it reads ring → paper gap → paint. Hover overlay is outline only, no knockout.
- **Halos are suppressed while dragging** (overlay passes skipped; lifted paint stays).
- Colors are CSS vars resolved once per theme: `--oblik-ink` (idle), `--oblik-accent` (editable, not hot), `--oblik-selected-paint` (**hover and selected share white/cream**), `--oblik-ring`, `--oblik-knockout` (paper). Muted = opacity 0.32. Fill alpha 0.16 idle, 0.28 hot.
- Chrome metrics (CSS px, defaults in `view/chrome.ts` `DEFAULT_CHROME_METRICS`): construction paint width **1.5**; ring `outlinePx` **7** (hover opacity 0.5, selected 1.0); `knockoutPx` **4**; points get wider halos — `pointOutlinePx` **14**, `pointKnockoutPx` **9**; point discs: derived **r 3.5**, editable **r 5**, paper outline stroke **2**; invisible hit target `HANDLE_R` **7**; snap radius `SNAP_R` **9**.

### Point marks and "handles" (there are no bbox grips)

Every point/glider node is **always visible** as a small disc (ink fill, paper outline; accent when editable; white when hot; bind label beside it when named). A `Handle` in `view/Hud.tsx` is an _invisible_ r=7 hit circle over editable points for placement-tool DOM snapping — not a visible grip. **"Drag handles write literals"** (pane status line) means: grab an _editable_ geometry node and drag, and its literal values are patched back to source (draft → commit):

| grabbable node                 | drag                 | written literal(s)          |
| ------------------------------ | -------------------- | --------------------------- |
| `point`                        | move                 | `[x, y]`                    |
| `glider` (segment/line/circle) | along carrier        | `t`, `s`, or `[ux, uy]`     |
| `circle`                       | rim (radius)         | radius, min 0.05            |
| `parallelLine`                 | perpendicular offset | distance off base line      |
| offset `csg2`                  | perpendicular offset | offset distance along stock |
| `slider`                       | HUD                  | scalar value                |

Segments/lines/circles are _not_ grabbable — clicking one selects it. Click-vs-drag is decided at release by travel ≥ **4 CSS px** (`PICK_CLICK_PX`); dead zones 2 px (edit) / 1 px (pan). Releases commit drafts and select via `onPick`.

### Placement tools, snapping, scopes

Space opens the tool palette; tools place geometry in steps with typed-arg prompts (Tab/Enter/Escape), ghost previews (dashed ink, ghost fill, offset arrow), and snap markers (circle for plain snaps, diamond at crossings). Snap targets: named points/gliders (`snapBoundPoint`), strokes/circles for glider placement (`snapStrokeCarrier`), sliders as length references. Scope focus (`select is scope`) restricts eligible snap carriers and mutes the rest.

## The pipeline model

### Picking model — pure CPU, reuse `euclid2/pick.ts` verbatim

Picking is **CPU geometry over the trace**, exactly the function the SVG view calls (`hitsNear` → `hitTest`), with no DOM dependency:

- **Rank order** (the "point beats line beats region" rule, already encoded): 0 point/glider → 1 segment/line/parallelLine/circle → 2 csg/pick → 3 region/polygon; then nearest distance; ties to the **later-defined node** (deterministic "on top").
- **Tolerances in CSS px**: geometry `GEOM_PX` 8, points `POINT_PX` 12; world radius = `px / scale` (SCALE_MIN 8 makes the guard harmless). Inside a fill (`d === 0`) always counts. AABB prefilter cached per node identity (P11's WeakMap).
- **No GPU pick target.** Rejected for three compounding reasons: MSAA resolve **averages** samples, so an ID attachment resolved from a hairline (2 of 4 samples covered) is garbage and WebGPU offers no "any-sample-wrote" resolve; pick geometry would diverge from visible geometry (fat bodies vs cores); and hover needs a result every pointer move — at today's node counts a CPU linear scan is free, while a GPU pick pass would need demand re-renders plus async readback plus throttling. The SVG view already _is_ CPU picking; full replication means reusing it. GPU instance-ID picking stays parked as the 3D rehearsal when 3D begins.
- **Body-pickable strokes**: a stroke is pickable when `dist(click, centerline) ≤ max(visual half-width, pickbox)` — the fat body is grabbable, hairlines always keep the pickbox floor. Same formula the GPU probe would have used, without a probe.
- **Cycling (new — SVG had none):** `onPick` receives the full ranked `hitsNear` list, not `hits[0]`. A **completed click** (down+up within the click dead zone — a click, not a bare pointer-up) whose top hit is the _already-selected_ node advances through the list; the next click on a different top hit resets to that node. Fills beneath strokes are already in the ranked list, so cycling reaches under.

### Render model — one ordered color target, chrome as extra draws

- Single color attachment, 4× MSAA, painter order: paper clear → grid/axes (instanced analytic hairline quads; axes recorded after the grid so they land on top, still under world ink) → **fills** → **ink** (strokes, then circles) → **points/chrome**. Translucent fills blend over paper/grid; ink always renders above fills — guaranteed by draw order, never depth. Chrome band passes interleave _within_ each band in the SVG order (idle paint, hover overlay, hover paint, selected overlay, selected paint) so halos land under their own paint yet above lower bands; while dragging, overlay passes are skipped.
- The `Frame` uniform already carries the chrome metrics and dash pattern (`outlinePx`, `knockoutPx`, `dash`, `dpr`); `RUN_DASHED` + `Frame.dash` exist for ghost previews and future dashed strokes.
- Fills come in two flavours, both analytic per pixel inside an AABB quad, and the adapter routes each node: **span fills** (analytic winding over a span array — polygons, picks, tool ghosts) and **compiled fields** (`csg2` and `region` nodes — see below). Chrome on a region/hot fill = **restroke its resolved loops** (outer + holes; `islandGeom`) as px-width outline/knockout strokes: segments → stroke instances, arcs/circles → the existing annulus instances.
- **Compiled CSG fields** (`gpu/field/`). A `csg2` tree whose operands are all single scalar fields is compiled instead of resolved: `plan.ts` walks the retained operand tree (`Csg2 = { op, of }`; leaves `region | circle | halfPlane | offset`) into a **shape** string, a leaf list addressed by comptime index, and a superset AABB; `assemble.ts` turns that shape into straight-line TGSL — ops fold pairwise into `min` / `max` / `max(a, −b)`, an offset is `child − d` (round joins fall out of the SDF shift, like `roundOffsetValue`), a `region` leaf inlines the same winding + nearest-boundary walk the span pass runs. Leaf reads are `fieldLeaves[base + <literal>]`, so the window base is the only runtime value. Consequences: **no island resolution on the CPU for trees** (the field is the union directly, one quad per node), exact arcs (no chord approximation), and — the property the cache rests on — **leaf numbers never reach the shader**: nudging every number leaves the WGSL byte-identical, so a drag can only rewrite data.
  - Reuse is keyed on the shape: 26 CSG fills across the demo scenes compile to **9 artifacts**, and a node's colour/alpha live in its quad, so hover/selection recolor without touching the shader either. A `pick` (island-restricted) and a `polygon` (not a `CsgOperand`) stay on the span pass by design.
  - Fills are translucent, so paint order matters and two pipelines cannot be merged into one draw: the adapter emits a **draw run per node** in band order (`FillDraw`) and the painter plays them back to back, using `firstInstance` to start each run in that pass's shared order array. One draw per fill node, exact SVG compositing order.
  - Pools are identity-keyed and byte-diffed like every other buffer: quads `MAX_FIELD_QUADS` 512, leaf records `MAX_FIELD_LEAVES` 4096, spans `MAX_FIELD_EDGES` 8192 (the field pool now carries the region load the span pool used to). A node that does not fit is skipped, the same failure mode as the span pools.
  - Tested without a device: `plan.test.ts` checks the TS twin of the shader against the CPU reference (`operandSdf`/`csgSdf`) on 12,690 probes — agreement to 1.3e-15 — and `wgsl.test.ts` resolves each shape through `tgpu.resolve` to assert the folded structure, the literal leaf offsets, the absence of op dispatch, and the byte-identical-under-data guarantee.
- Points: **filled disks from the `@typegpu/geometry` disk primitive** (`circle` + `circleVertexCount`, `gpu/pipelines/disks.ts`), emitted as concentric layers per mark replicating the SVG `PointMark`: paint disc at mark radius, the always-on paper rim just outside it, and halo ring/knockout discs _beneath_ the paint — the halo covers earlier bands but never the point's own paint. Points ride the adapter feed with the other drawn nodes.
- Handles, sliders, bind labels, palette prompts, and all **text is HTML** — in the WebGPU view text is an HTML overlay on the canvas, not GPU glyphs and not SVG (SVG is too limiting for chrome text: no padding, etc.). World-anchored text (bind labels) is positioned per frame from the same world→screen mapping (`worldToScreen`, CSS px); sliders/HUD are HTML controls. Geometric chrome that needs no text (ring/knockout, snap markers, ghost, point halos) stays GPU geometry.
- **Bind labels** (`euclid2-typegpu/BindLabels.tsx`): one `<span>` per named point/glider — exactly the SVG point band minus its overlay passes (`isBindLabelNode`) — inside a pointer-transparent layer that copies the paper box. Position is `worldToScreen(anchor) + (10, −8)` (the SVG `<text x/y>`), lifted by the line-box height because SVG's `y` is a baseline and HTML positions a line box by its top; the shift rides `transform`, so a camera move only recomposites. Camera/pane are reactive props, so labels follow the painter tick. Muting matches `PointChrome` (`mutePoints`, or out-of-scope, and never while hot/selected). Because the layer is HTML it paints **above all GPU geometry** (SVG draws labels inside the point band), and it is hidden until the first frame lands. The offset/color/size contract lives in `docs/chrome.md`; the two views were compared side by side and match.
- **Ghost previews**: dashed strokes via `RUN_DASHED`, translucent ghost fill via the fill pipeline, arrowheads already exist in the vendored cap set. Snap markers are GPU geometry (circle for a plain snap, rotated square for a crossing) — they carry no text, so nothing about them wants HTML.

### Units model — DPR-sensitive, every look knob in logical px

**Rule: all look-knob constants are logical (CSS) px.** The only place `dpr` appears is the canvas backing size and the world→NDC mapping; it is **never** multiplied into a knob, and the NDC mapping must never be changed to compensate for a knob. Concretely: `size`/`pane` stay CSS px, the canvas is `size × dpr` device px, `Frame.dpr` rides along for anything genuinely pixel-sized (e.g. `fwidth` AA), and every knob converts to world units once as `px / scale`. Result: a 1 CSS px hairline covers `dpr` device px at any zoom, identical on retina and standard displays — which is what the SVG `vector-effect: non-scaling-stroke` + CSS-px widths already deliver and what the GPU must match. Audit target: the grid hairline (must be **1 CSS px**; verify `grid.ts` against this rule) and every chrome stroke/annulus/disc radius above.

Known deltas in the ghost layer: the region preview closes its partial chain back to the start vertex with a straight segment (the SVG path closes the same way, but arc edges are approximated in the chain's shoelace orientation test); trace-ghost region fills are not drawn yet (ink only); and a round ghost dot coincident with the crossing diamond is suppressed — the small diamond's inradius (SNAP_DIAMOND_R/√2 ≈ 3.5px) is under the 4px ghost dot radius, so the two together read as a circle.

The SVG view stays the reference implementation; the WebGPU view must not change eval or pick semantics — identical trace in, identical interaction out, different raster.

## GPU capability survey — what the renderer is not using yet

The GPU surface actually in use is **one color attachment at 4× MSAA**: no depth, no stencil, no compute, no offscreen color target (capture resolve aside). Hover/selection chrome is CPU-chosen band recolor plus chrome geometry strokes (disc layers shipped; region restroke still pending) — deliberately, per the models above.

**Design decision — translucency gates only the occlusion-family tricks.** World fills stay translucent (alpha over paper/grid); ink edges always render above fills. Ordering is painter order, never depth. Stencil is _color-agnostic_: stencil-then-cover fills and clip masks work unchanged for translucent fills. What translucency precludes is expressing _overlap between separate shapes_ with masks: a stencil test is binary keep/kill before blending, so masks are set semantics (one shape owns the pixel), while translucent overlap needs both shapes to contribute — ordered alpha blending only. Depth ordering and stencil-encoded cross-node subtraction stay out while fills blend.

- **Depth buffer.** Additive on installed typegpu 0.12.5; would buy draw-order freedom and 3D plumbing rehearsal but breaks translucent compositing (unsorted alpha). Revisit when an opaque pass exists or 3D starts.
- **Stencil buffer** (Skia GPU backend / NV_path_rendering territory): _stencil-then-cover fills_ (even-odd parity, O(1) fragment cost, AA from MSAA) is the standing benchmark vs the analytic winding fill; _clip masks_ (stencil `equal` while stroking) would replace CPU clip-geometry surgery. Stencil-CSG _subtraction between separate nodes_ is mask-encoded occlusion — wrong compositing for translucent overlap, not because stencil needs opaque colors.
- **GPU picking.** Revisited and **not adopted** (see Picking model): CPU `hitsNear` is the SVG behavior, free at today's counts; MSAA resolve averaging corrupts any resolved ID attachment. Parked as the 3D picking rehearsal.
- **GPU-native selection chrome.** Adopted as the plan above: no new pipeline — the selected node's resolved loops re-stroked at px widths (segments → stroke instances, arcs/circles → annulus instances), points as disk + ring bands. Jump-flood (`@typegpu/sdf`) stays in reserve for deep-CSG silhouettes / mass selection.
- **Offscreen layers / pixel caching**: fights the thesis (re-rasterization is cheap; camera moves invalidate caches). Scale play for 10⁵+ nodes; not this prototype.
- **Compute**: (1) _grid hairlines_ — done as an analytic instanced pass, not compute; (2) _dashes_ — `RUN_DASHED` + `Frame.dash` reserved but dead; arc dashes are analytic from the sweep angle; (3) _jump-flood chrome_ in reserve.
- **OIT, drawIndirect, occlusion/timestamp queries**: real but later; only timestamp queries serve the fills benchmark now.

## Environment questions

- WebGPU in the demo's browsers: Chrome/Edge fine; Safari/Firefox status to verify. Headless chromium (Playwright rig) needs `--enable-unsafe-webgpu` / SwiftShader fallback — confirm the rig can render, or test logic headless and pixels by eye.
- Fallback when `navigator.gpu` is absent: no capability check at the renderer switch — the WebGPU view's init reports "WebGPU unavailable" and the per-scene SVG option of the chip keeps serving the scene.

## Locked

- One `TgpuRoot` for the app lifetime, created lazily on first `TypegpuView` mount; destroyed on HMR of the renderer, never per-eval.
- **Renderer switch is per-scene, inside the euclid2 pane** — `<Dynamic component={gpu ? TypegpuView : Euclid2View}>` swaps implementations; the choice persists per scene file (stored signal), defaults to GPU, and never touches eval or scene kinds (kind stays `figure` vs `euclid2`).
- Camera + pane + chrome metrics live in the `Frame` uniform (one write per view sync); node data lives in storage buffers written per tick as byte-diffed patches keyed on node identity (P11). Grid: one `GridSpan` uniform per sync.
- **Picking is CPU** — the shared `euclid2/pick.ts` runs in the WebGPU view unchanged: same ranks, same CSS-px tolerances, same AABB prefilter, body-pickable rule. **No GPU pick target.**
- **Cycling** on repeated completed clicks advances the ranked candidate list (new behavior, not present in SVG).
- **Fill trees compile; they do not re-resolve per frame.** A `csg2`/`region` fill becomes a shape-keyed field whose WGSL depends on the tree's shape only — leaf numbers, colour and alpha are data. Rebuilds happen on a **shape change** (an operand added/removed, an op changed, a leaf kind changed) and nowhere else; the pipeline cache is keyed on shape + target, and the fragment/WGSL is built once per shape. The CPU keeps `evaluateRegions` for picking and for the span-pass fallbacks (`polygon`, `pick`, tool ghosts) — never for a compiled field's pixels.
- **Chrome metrics and all look knobs are logical (CSS) px**; dpr enters only at canvas/NDC mapping, never into a knob. Grid hairline = 1 CSS px.
- **Text is HTML** (bind labels, slider HUD, chrome text) — never SVG or GPU glyphs in this prototype. Bind labels own a pointer-transparent layer over the canvas and follow the camera from `worldToScreen` (`BindLabels.tsx`); they therefore paint above all GPU geometry, where SVG draws them inside the point band.
- **Points/gliders render as GPU disks** through the `@typegpu/geometry` disk primitive (`disks.ts`) and are in the adapter feed.
- SVG HUD semantics are the contract (`view/marks.ts`, `view/chrome.ts`, `view/pointer.ts`, `pick.ts`); the WebGPU view reuses their logic and reproduces their pixels.
- The eval layer must not know the renderer exists: no GPU types in `eval/*`, no renderer-owned fields in trace nodes. The adapter maps tape → GPU state.

## Open questions for the spike

1. Stencil-then-cover fills vs the analytic winding fill: at what edge count and zoom does even-odd parity + MSAA beat the O(edges × pixels) walk? The live case is the **polygon** fill (gear: 1521 spans in one island, every covered pixel walking all of them) — compiling a tree does not help there, so the lever is per-tile span binning (compute-built, so the CPU stays out of it) and/or splitting segment spans into a slimmer record than the arc-carrying one.
2. Buffer update strategy in practice: how much of a tick is a patch vs a rewrite (a bead drag in cache-lab should be one slot)?
3. Line dashes and variable screen-space widths — the things SVG gave free that the GPU must write by hand; `RUN_DASHED` + `Frame.dash` are the reserved seam.
4. Ring/knockout restroke vs jump-flood chrome: at what silhouette complexity does per-loop restroking lose, and does mass selection change the answer?
5. HTML overlay placement cost for world-anchored labels at high node counts (labels follow geometry each frame). Answer so far: one `<span>` per **named** point/glider, moved by `transform` only — a camera move is compositing, not layout, and the text matches the SVG view pixel-for-pixel; the SVG view pays the same text cost per frame inside the hud SVG. Untested beyond the demo scenes' node counts.

## Not this prototype

- 3D scenes, perspective cameras, depth — the 3D move comes after this renderer proves lifecycle, upload, picking, and chrome. GPU instance-ID picking returns with it as the rehearsal.
- Replacing the SVG renderer or touching its code paths: the WebGPU view is an alternative implementation mounted through the euclid2 pane's SVG | GPU switch, never a replacement.
- GPU particles, post-processing, shadows, offscreen pixel caching, OIT, drawIndirect.
- Changing the eval layer, site memoization, or user `memo()`.
- Text rendering on the GPU; SVG as a chrome/text layer for the WebGPU view (HTML replaces it).
