# Prototype 13 — tracing a raster reference: an `image(...)` trace node

**Status:** built — the node, the wire, the GPU layer, import (paste, drop, picker, dropped path) and the inspector all ship and are used. **The known-distance measure and canvas drag-to-move were cut from this prototype**, not left open inside it (see "Not this prototype"): both are their own slice, and neither is needed to trace a reference. The charter comes from the [P12 postmortem](./12.md) — the convention recorded in [`intent.md`](../intent.md), "the next charter is written from the postmortem".

## Why

The sketch cannot hold the thing being traced. You measure a known distance, rotate, flip and position the reference in an external editor, then draw next to a picture that is not on the paper — and when the scene file moves, the reference does not come with it. `intent.md`'s horizon has an unrelated package consuming an exported artifact "even a PNG"; the useful half now is the inverse, a reference the scene **owns**.

## Locked (product)

**Storage is an asset file, not source.** The bitmap is written to `<appRoot>/public/assets/<slug>-<hash>.<ext>` and served by Vite at `/assets/…`; the scene source holds only the URL. No base64 in source, and no import line either — Vite's `publicDir` serves that directory at the root, so `image("/assets/gear-9f3a2c11.png", …)` just resolves. A dropped path that is **already inside `publicDir`** is used where it lies: the node holds that file's own URL (`/assets/ref.png`) and nothing is copied.

**The plugin serves those assets, not Vite.** Vite reads `publicDir` **once at startup**, so a file an import writes afterwards is invisible to its own middleware: the request falls through to the SPA shell as HTML, which is the file the browser then fails to decode (and the renderer's texture load fails the same way). So the plugin answers `GET /assets/<image>` from disk itself — image extension, no path separators, file must exist — before Vite's middleware sees it.

**Any format the browser can decode; nothing else.** The acceptance test is `createImageBitmap(blob)` resolving. PNG, JPEG, WebP — whatever the browser decodes — is stored as given, so the extension follows the source rather than being forced to `.png`. A format the browser cannot decode is dropped **before** upload, with an error, and writes nothing.

**Four ways in.** Paste a screenshot from the clipboard, drop bytes on the canvas, pick one from the Space palette, or drop a _path_: an embedded browser (VS Code's explorer) hands a drag over as URIs with no bytes in it, so the dev server reads that path off disk and stores it like any other import. A _local_ path is not the remote-URL case that stays out of scope — no network, no SSRF — and `resolveDropFile` is the boundary: inside the project root, an image extension, under the cap. Pasting an image **URL** is deliberately out of scope: it would need the plugin to fetch the URL server-side to dodge CORS, which brings a size cap and an SSRF surface this prototype should not absorb. The three byte-paths share one pipeline.

**The image is a trace node like any other.** `image(...)` takes an `id`, has an occurrence, is selectable, editable in the source text, and patchable through an endpoint — the same contract as `point`, `region` or `slider`. It is a parallel `TraceValue` arm, not a `Geom` and not a `CsgOperand`: nothing composes it, it never enters a CSG tree, and it is not an operand.

**Import size follows the view it landed in.** The charter first said "1 bitmap pixel = 1 world unit, and fitting it to the pane is a camera move". That cannot work here: this camera's zoom floor is 8 px per unit, so a 400-pixel screenshot at pixel scale needs a zoom of ~1.7 to fit at all — fitting would mean changing the app's whole zoom range, and the pick radius floor (`px / max(8, scale)`) that assumes it. So the import _states a size_: the bitmap's centre lands on the drop point, one `targetSize.width` is written — what `fitWorldWidth` says shows the whole file in the view you dropped it into — and the height is left to the aspect. The node holds an explicit world rect — `imageRect` derives it from the stated sizes, and nothing is async — and the reference is visible the moment it lands. Its _true_ scale is **stated, not measured** — the postmortem's known-distance correction is a later slice, and until then the inspector's numeric fields are how a wrong one is fixed.

**Pick priority is below regions** — an image is grabbed only when nothing else is in reach.

**The inspector is the transform UI**: rotate in 90° steps, flip, the style dials, and the numeric placement and target size. There is no on-canvas transform tool and no bbox grips — a reference is placed by its `world`, which is a `Vec2` like any other, so pointing it at a traced point makes the picture follow that point and no drag gesture is needed to move it.

## The node

Props arrive as an options object, so a reference reads as named fields and a later prop does not renumber every call site:

```ts
image(src: string, opts: {
  world: Vec2;                                     // where it goes — a point() drops straight in
  anchor?: Vec2;                                   // the bitmap pixel that sits there (default its top-left)
  imageSize: { width: number; height: number };    // the bitmap's own pixel size
  targetSize: { width?: number; height?: number }; // the world size; one side infers the other
  rot?: 0 | 90 | 180 | 270;                        // default 0
  flip?: 0 | 1;                                    // default 0
  style?: { opacity?: number; saturation?: number; contrast?: number };
}, id?: string): Image
```

- **`world` + `anchor` is the anchor point** — After Effects and Figma's name for it; Flash called it the _registration point_, Illustrator the _reference point_, a game engine the _pivot_, and paired with a surveyed coordinate it is a _control point_. `world` is where the reference goes and `anchor` is the pixel of the bitmap that goes there; the rest of the picture follows. The default anchor is the bitmap's **top-left**, so the picture hangs down and to the right of `world` — the reading SVG, canvas and CSS all have. An `anchor` of `{ x: width/2, y: height/2 }` places it by its middle, and any other pixel pins the reference to the feature being traced.
- **A traced point is a `Vec2`**, so `image(src, { world: P, … })` attaches the reference to it: eval reads the point's coordinates, and moving the point moves the picture. Same dependency shape as `circle(P, r)`.
- **Image space is pixels with y running down** from the top-left — the way the bitmap and the uv table are numbered — while world y runs up. That is what makes the picture upright by construction rather than by a uv convention: the bitmap's top-left is the rect's `(x, y+h)` corner. `imageRect` (`eval/image.ts`) is the only place the conversion happens.
- `targetSize` states the world size. **One side infers the other from `imageSize`'s aspect**; both sides allow deliberate distortion. `imageSize` is what the aspect comes from and it is _stated in the script_ rather than read from the file, so evaluation stays synchronous and nothing decodes — the reason the earlier "infer from the asset" idea died was that decoding is async, and async in a scene colours everything.
- `style` is three independent dials rather than one "fade": `opacity` multiplies the bitmap's own alpha, `saturation` mixes between the bitmap's grey and the bitmap, `contrast` scales about mid-grey. Because the reference layer draws first on the cleared paper, `opacity` _is_ "fade toward paper" — the blend does it — so the shader holds no paper colour and a theme switch needs nothing from the image layer. Defaults are neutral (1, 1, 1): the bitmap as it is, with the starting look being the import flow's business.
- `rot` turns the rect about its own centre in 90° steps, and a positive `rot` reads counter-clockwise on screen — world +y is up on screen here, so model and screen agree — and `flip` mirrors it about the vertical centre axis. (Open question, not built: making the _anchor_ the pivot instead — the AE/Flash reading, where the pinned pixel never moves — is a small change to `imageCorners` if the tracer's workflow wants it.)
- **The tape holds the authored props, not a resolved rect.** `ImageValue` is `world`, `anchor`, `imageSize`, `targetSize`, `rot`, `flip`, `style` and the source — the same fields the call states, with the look dials' defaults filled — and `imageRect` turns them into the world rect at the leaves that need geometry (pick, the quad, the bounds). That is what lets the inspector show and edit exactly what the source says: a resolved rect cannot tell you where the anchor was, and two different authored nodes can draw the same quad.
- `image` registers as a traced constructor with its `mark(...)` site spec, in the same constructors object as everything else, so insert / patch / mention / stamp keep working unchanged. Patch schema follows `paintPatchSchema`/`parsePaintPatch`; the edit function follows `source/paint-edit.ts`, writing dotted leaves (`world.x`, `targetSize.width`, …) and creating the branches a call does not carry yet.
- `dof` is empty, on purpose: the numeric props live _inside_ the options object, where the positional literal patcher (`source/patch.ts`) cannot reach them. So a reference is not literal-editable and has no draft path — the patch endpoint is its only writer, and the inspector is the only caller.

**Pick arms** (`euclid2/pick.ts`), explicit in all four places rather than falling through the default rank:

| function        | image                                          |
| --------------- | ---------------------------------------------- |
| `isFiniteTrace` | true (a finite rect picks like any other fill) |
| `geomDistWorld` | distance to the rotated rect; inside → 0       |
| `aabbOf`        | the rotated rect's AABB                        |
| `pickRank`      | **4** — below `region`/`polygon` at 3          |

## Import

One pipeline, three adapters. All three converge on a `Blob` before anything is uploaded.

- **Paste.** A `paste` listener, not a keydown handler: a `KeyboardEvent` carries no clipboard data, and `navigator.clipboard.read()` is permission-gated. Iterate `clipboardData.items` and take `item.getAsFile()` — `clipboardData.files` is empty for a pasted bitmap in most browsers, and fills only when the clipboard holds real files (a PNG copied in Finder), which is the second case to support. Guards: skip when the target is an `HTMLInputElement`/`HTMLTextAreaElement` (the inspector's numeric fields must receive a pasted value), and skip when there is no image item and the clipboard has text. No location → the viewport centre.
- **Drop.** `dragover` + `drop` on the paper element, with `preventDefault()` on `dragover` — without it the browser navigates to the file and the scene is gone. The drop point, in world coordinates, is the image's centre. Two payloads are accepted: `files`/`items` when the drag came from the OS, and — when the drop is all text (`text/uri-list`, `resourceurls`, `codefiles`, `text/plain`) — a `file://` path, which `POST /__oblik-import-path` resolves and stores before the browser decodes the copy it serves. A drop that yields neither says what it carried, payload text included, because that text is the only way to tell which dialect to support next.
- **Picker.** `<input type="file" accept="image/*">` behind an "Import PNG" affordance in the inspector.

**Validation happens client-side first**: decode, size cap, MIME → extension. A rejected drop must not leave an orphan in `public/assets/`, and the order is decode _then_ upload — the browser is the only format oracle there is, so a file it cannot draw never reaches the server at all. The path route cannot keep that order — the browser has no bytes to decode until the server has stored them — so it stores first and decodes the copy it serves: a file whose extension lies is the one case that can leave an asset behind.

**Paste and drop are in; the picker is the inspector's.** A `paste` listener and a `drop` on the paper element both funnel into one `(file, world)` call; the `<input type="file">` sits behind the inspector's import button, which arrives with the inspector.

**Naming is content-addressed.** The client sends a slug; the **server** sanitises it, hashes the bytes (`sha256`, first 8 hex) and writes `<slug>-<hash>.<ext>`. Identical bytes reuse the existing file, distinct images can never collide or overwrite, and the client cannot influence the path. The endpoint creates the directory (the demo has no `public/` yet), stays inside `resolveUnder`, and returns the served URL. Then the existing `/__oblik-insert` writes the node — two POSTs, so a failed insert leaves the asset on disk; that is accepted and surfaced, not silent.

The endpoint is a plugin change, so the dev server needs a **restart** before import can be exercised (the asset directory itself needs none).

## The GPU layer

An image is a textured quad drawn in the existing single pass, **immediately after `beginRenderPass` and before the grid**, so the reference sits under grid, fills, strokes and points. One pass — a second attachment would need `load` instead of `clear`.

- A cache keyed on `src` loads asynchronously: `createImageBitmap` → texture → sampled view with a linear, clamp-to-edge sampler. `createImageBitmap` is the _only_ format-specific code in the system, which is what makes "any decodable format" cheap. A 1×1 transparent placeholder covers unloaded and missing sources. Loading stays **outside eval**; textures are destroyed on unmount and a frame is requested when one becomes ready.
- The fragment applies the three dials in order: `grey = mix(vec3(dot(rgb, luma)), rgb, saturation)`, `rgb' = saturate((grey - 0.5) · contrast + 0.5)`, `alpha' = alpha · opacity`. No paper colour in the shader — the blend against the cleared paper is what makes a faint reference read as faded, which is also why a theme switch is free here.
- **A reference's selection chrome is the region chrome**, and the shader proves it by calling `haloColor` and `edgeCoverage` from `halo.ts` — the same two functions a fill's boundary runs. The only new thing is where the distance comes from: a fill has a boundary walk and gets a signed distance to it, a reference has a quad, so its distance is the uv inset to the nearest border scaled to CSS px by the rect's own world size and the frame's zoom. That is the whole trick: the band follows a rotated quad for free, the width stays a screen width at any zoom, and a zoom still writes no record. Hover is the ring at 50% with no gap; selection is the ring opaque plus the paper knockout just inside it, with the node's own outline in the selected paint over that — only its inner half lands, since the outer half is outside the quad.
- **A cold reference carries no chrome at all.** A fill's own outline is always on (ink when cold) because it _is_ the fill's ink; a reference has no ink, so a border around every one of them would be noise. The halo's alphas would draw nothing anyway; this is about not asking for it.
- **The paper is not the image layer's business.** An earlier design mixed toward `theme.paper` in the fragment; `opacity` as alpha does the same thing through the blend, so the uniform, the binding and the `setTheme` hook are all gone rather than kept for symmetry.
- The quad is the node's rect transformed by `rot`/`flip` — CPU-side, so the shader only samples.

## Inspector

- The inspector composes the existing sidebar pieces (`SelectionSidebar` with children, `SidebarSection`, `NumberField`, the shared button classes) and writes every change through the patch endpoint — `ImageInspector`. It shows the **authored** props, which is why the _stated_ target side is the one that gets a field: a node written with only a width keeps inferring its height, and the field that would freeze that is not the one on offer. Import is the **palette's** action, not the inspector's and not a button on the paper: a reference is imported, not drawn, so it has no ghost, no args and no session — the Space palette carries an `Import image` entry (`ACTIONS`, kept out of the constructor list) that opens a file picker instead of starting a tool. A picked file takes the same path as a paste, placed at the middle of the view. The reference section itself sits above Origin: what you selected comes before where it came from. The view reports where it is (`onView`) from the handlers that _move_ it — a pan, a zoom, a resize — the same shape as everything else it tells the pane, rather than from an effect watching the camera.
- **Every edit previews, then writes once.** A dial drag and every keystroke set a pane-local override that the evaluated tape reads through `withImageOverride` (`euclid2/imageOverride.ts`), so the canvas follows the gesture without touching the file; the release or blur sends one patch, and a failed patch drops the override rather than leaving a value the source does not have. The override also remembers the source value the preview started from and applies only while the source still says it, so anything else that moves the reference — an edit in the file, or a point the picture is tied to — is not masked by a preview that is still live.

## Pass / fail

**Pass.** Paste a screenshot with the canvas focused → a file appears under `apps/demo/public/assets/`, the URL loads, and the image draws under grid, fills, strokes and points. Paste with a numeric field focused edits the field instead. Paste text → nothing. Drop a file on the canvas → it lands centred on the pointer, sized to the view, and the page does not navigate. Drop something the browser cannot decode → an error, and no file on disk. Rotate 90/180/270, flip, the style dials (opacity, saturation, contrast), numeric placement and target-size edits — all reflected in the scene source, and on reload the node comes back from source with its id. Toggle the theme → the desk and a translucent reference both move to the new paper colour (an opaque one does not, which is correct: it is a photograph). Click over an image near a point or a region → the point or region wins; click bare image → the image is selected. Edit the node in the source file → the canvas updates.

**Fail would have been:** base64 in the scene source; a second renderer pass; an image node eval has to know the pixel size of; decode inside eval; on-canvas transform handles; a name the client chooses for a path; storing a format the browser cannot decode; pasting a URL through the page; an image that outranks a region in the pick order; a transform that writes the source once per pointer move.

## Not this prototype

- Fetching a remote image URL server-side (a follow-up, with a size cap and its SSRF note).
- **Scaling from a known distance** — the measure the [P12 postmortem](./12.md) proposed. It is not hard arithmetic: click two points over a known length, and the scale is `D / |AB|` applied about the first. What it needs is a crosshair mode that steals the canvas clicks from pick and pan, a ghost on the second click, and a way to ask for `D` (an inspector field, or a dialog after the clicks). That is a gesture slice, not a corner of this one, and the inspector's numeric fields cover the case in the meantime.
- **Drag-to-move on the canvas.** `world` is a `Vec2`, so `image(src, { world: P, … })` already moves with the point `P`, and that is how a reference is repositioned today. A canvas gesture would be convenience on top of the pane-local override the inspector's previews already use, not a capability the node lacks.
- Cropping, opacity masks, multiple images per node, image re-import or re-linking.
- Non-uniform scale _tools_ (the fields allow it; nothing drives it as a gesture).
- Bitmap export or embedding the asset into an exported artifact.
- Image nodes in `figure/`, or anything that makes an image a `Geom`/CSG operand.
- Vectorising, autotracing, edge detection.
